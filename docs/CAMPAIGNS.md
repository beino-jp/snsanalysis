# 案件の目的スコア・インフルエンサー推薦（モックデモ）

## 今回使える機能

「候補を探す」から、目的入力 → 足りない条件の補足 → 評価基準確認 → 比較 → 最大10人の推薦を試せます。
デモは100アカウントの固定された架空データを使います。Instagram検索・Apify・OpenAIへの通信は行わず、利用料は0円です。
候補はプロフィールと直近20投稿までを比較します。反応ユーザーの取得、フォロワー一覧の取得、365日分の全投稿分析はこの検索の範囲外です。

## 3,000円の予算

1回の候補検索の外部API利用料予算は、サーバー側で3,000円に固定しています。クライアントから引き上げることはできません。
`discovery_jobs` に上限・実績・予約額、`discovery_charges` に処理ごとの費用を記録します。
外部呼び出しの前に最大額を予約するための `reserveCharge` はDB行ロックを使い、実績＋予約＋新規予約が上限を超える場合は拒否します。
確定額は `settleCharge` で一度だけ反映。予期せず予約額を超える請求が観測された場合は、後続処理を停止します。
モックでは全処理の予約・実績とも0円で、この予算処理の流れを試します。

**実データで3,000円以内の請求を保証する実装は、まだ完成していません。**
実検索の接続前に、下記を必ず実装・検証する必要があります。
- 採用Apify Actorの検索・プロフィール・投稿の入力/出力、取得上限、開始料金、最低料金、失敗時の課金を契約テストで確認。
- 検索件数100、各人の投稿20件という取得上限をActor側でも強制。
- Actorの `maxTotalChargeUsd` と、OpenAIを使う場合のトークン上限をサービス側でも設定。
- USD/JPY換算、税、カード手数料、為替変動余裕を含む円換算の予約額を計算。実行開始時のレートと料金表を固定・保存。
- 実行IDの保存と課金の照合、不明な請求が残る場合の停止、外部保存先の画像・個人データ削除。
- サーバー代・月額最低料金・開発費は、この1検索の予算と別管理。使用枠の二重加算を避ける。

現時点の検索登録は常にmock Providerであり、APIキーを設定しても有料検索へ切り替わりません。料金上限の設定だけで実サービスへの送信が始まることはありません。

## 評価は2種類

### 1. 新しい候補の発信内容の適合スコア

固定ルール（暫定の製品基準、業界標準ではありません）：

| 項目 | 配点 | 算出 |
|---|---:|---|
| 発信テーマ | 40 | 直近20投稿中のテーマ言及数。投稿数の40%（最低3投稿）を満点目安 |
| 対象層に関連する発信 | 25 | bio/投稿の対象層に関連する明示語。実際の反応ユーザーの属性とは区別 |
| 対象エリア | 15 | bio/投稿での地域の明示。記載がなければ不明。「全国」は地域制限なし |
| 最近の発信活動 | 10 | 過去30日で4投稿を満点目安 |
| 投稿への反応 | 10 | (いいね+コメント)/フォロワー数の中央値。3%を満点目安。欠損は不明 |

テーマ関連の投稿があり、60点以上・情報充足率70%以上の公開候補をスコア順に最大10人推薦します。
鍵アカウント・未成年の可能性がある候補は除外。該当者不足なら10人未満、ゼロ人でも返します。
未知の項目を除外して100点に再換算しません。観測できた点数と情報充足率を表示します。
同一ユーザーを重複推薦しません。画像は使用・保存しません。スケート案件でスケボーの投稿を同じテーマの根拠にしません。

### 2. 既存PR投稿の目的への到達スコア

完了済みPR投稿を任意で選ぶと、保存済み判定を再取得せず使います。
- 対象層への到達、テーマ関心、対象年代のうち、指定条件に対応する項目を採用。
- 配点の合計は100。ユーザーが配点と満点になる目標割合を確認・変更してから実行。
- 得点＝配点×min(該当ユーザー割合÷目標割合,1)。分析済み公開アカウントが分母。不明を含みます。
- 対象層のタグが複数あっても同じ人は1回（OR条件）。
- 30人未満・情報充足率70%未満は「判定材料不足」。取得率20%未満または不明は参考評価として目立つ警告を表示。
- 80点以上は「設定目標をおおむね達成」、50点以上は「改善の余地あり」、それ未満は「設定目標への到達が少ない」。あくまで設定目標に対する評価。
- 未対応テーマの関心や、地域・実来場・購買・ROIは推測で埋めません。

## 目的の聞き返しとProvider

デモの目的整理はルールベースです。目的文から読み取れない「成果・対象層・地域・ジャンル」を聞き返します。
ジャンルが未知でも、フォームで指定すれば候補のキーワード比較はできます。対応する反応ユーザーの属性がなければ既存投稿の評価は不明になります。
`CampaignLLMProvider` を `LLMProvider` の派生インターフェースとして分離しており、将来のOpenAI接続に置換可能です。現在はOpenAIによる自然言語理解・判定は未接続です。
`DiscoveryDataProvider` は既存 `DataProvider` とは別の探索操作を担当する派生インターフェース。実データでの新規候補発見は未接続です。

## 保存と再現性

目的、確認済み配点と目標、ルール版、基準日時、Provider、候補の評価内訳、元投稿ID、費用を保存します。
非同期ワーカーは候補単位で保存し、取得済み候補を再処理せず再開可能。
候補データ・検索履歴・費用台帳は90日で削除します。ワーカーの稼働が必要です。
健康・宗教・政治などの敏感な属性は条件から拒否します。

## Macで更新

1. デモのターミナルで Control+C。
2. 更新ZIPをダウンロードして以下を実行。

```bash
unzip -o ~/Downloads/reach-insight-campaign-update.zip -d ~/Downloads/reach-insight
npm run db:setup
npm run dev
```

`db:setup` は追加テーブルを作るだけで、既存データは削除しません。
ブラウザーを再読み込み → 左メニュー「候補を探す」 →「スケート案件の入力例を使う」で試せます。
